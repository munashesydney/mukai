# Custom capabilities

Capabilities are actual `.ts`, `.js`, `.mjs`, or `.cjs` modules saved in a connected workspace. The authoring interfaces live in `src/shared/customCapabilities.ts`; this folder includes runnable TypeScript and JavaScript examples. When copying the TypeScript example into another workspace, remove its repository-relative type import and `satisfies` expression, or copy the contract and adjust the type import.

VM workspaces use the same registration tools and UI. Save modules inside `/home/mukai/workspace` and provide a relative module path. Install dependencies inside that VM. Compilation, import validation and handler execution happen in the guest, while Mukai's controller stores the compiled version and manages permissions, environment variables and durable jobs. Routes remain hosted by Mukai and invoke their guest handler over the authenticated bridge; no guest port forwarding or listener is needed. Controller helpers (`enqueue`, `wakeBot`) await persistence before returning. Startup reloads saved registration metadata without booting VMs or importing guest code on the host. The VM starts when registration validation or execution needs it. A failed/disconnected guest returns an error; uncertain in-flight calls are not automatically replayed.

`npm run test:capabilities:vm -- --data-dir PATH` verifies registration, Linux execution, HTTP routes, exact webhook bytes, durable helpers and saved versions after VM restart using a disposable copy of the prepared base from that data directory. Build the guest bundle first. Personal workspace disks are never opened. Existing base images may need internet access to install the compiler dependency in the disposable copy.

Write a module, then call `register_custom_tool` or `register_custom_route` with `{operation:"register",modulePath:"capabilities/example.ts"}`. Default exports are used unless `exportName` names another export. Updates take the registration `id` and `operation:"update"`; enable, disable, remove, list, and inspect use the same built-in tools. A new tool is available on the next model step of the current turn. Custom tools are available by default to all bots in the workspace; explicit per-bot tool assignments and configured execution approvals still apply. Any bot with the relevant registration tool can inspect, update, enable, disable, or remove registrations in its workspace, including those created by other bots or through the UI. Creator metadata is retained for default webhook wake routing, not editing or execution access. You can manage every registration from the existing Tools page.

Custom tool registration also requires `permissionMode`: `auto_approve`, `ask_bot`, or `user_approval`. This is a registration setting, not a field in the module. For example: `{operation:"register",modulePath:"capabilities/revenue.ts",permissionMode:"auto_approve"}`. Choose based on the tool's effects; keep drafting and sending in separate tools when they need different policies. Routes have no permission mode. Existing tools without a mode are upgraded to `user_approval`. Change the mode in Custom Tools or use `{operation:"set_permission",id,permissionMode}`; updates preserve it unless a new mode is supplied.

`auto_approve` executes bot calls immediately. `user_approval` waits through Mukai's regular approval UI, including in Full access. `ask_bot` does not execute the module: it returns a normal `confirmation_required` result with the exact proposed arguments and a `pendingCallId`. The bot then calls `confirm_custom_tool({pendingCallId,decision})` with `continue`, `ask_user_approval`, or `cancel`. This checkpoint is expected, not a tool failure or an indication that the task is forbidden. Continue executes the saved invocation once; escalation waits for user approval even in Full access; cancellation or denial executes nothing. Confirmation is bound to the bot, conversation, run, arguments, and code version. Current tool availability and assignments are rechecked before execution. Changed tools require fresh calls; stopped/completed runs discard pending confirmations. Running calls with uncertain outcomes are never automatically replayed. The inspector's Test button explicitly runs the module as a user-initiated test; it does not simulate the bot permission flow.

Tools export `{name,description,inputSchema,requiredEnv,execute(args,context)}`. `inputSchema` is an object JSON Schema validated before execution. Routes export `{name,method,path,auth,requiredEnv,handle(request,context)}`. Exact methods and paths under `/custom/` are supported; parameterized paths and catch-all routes are not supported in this version. A handler returns `{status,headers?,body?}`; object bodies become JSON and string bodies default to plain text. Route tests take `{headers:{},rawBody:"exact UTF-8 request text"}`.

Inside `execute`, `handle` or `processJob`, use `await context.callRoute(routeId, request)` to call a registered route in the same workspace. The route ID comes from `register_custom_route` list or registration results; its registered method and path are used automatically. The optional request accepts `body` (JSON), `rawBody` (exact UTF-8 text), `headers` (string values) and `query` (string values). `body` and `rawBody` are mutually exclusive. JSON bodies default to `Content-Type: application/json`; raw JSON needs that header explicitly. Headers are normalized to lowercase and transport headers are rejected. The result is `{status,headers?,body?}`, including non-success statuses returned by a handler. Invalid registrations or runtime failures reject the promise. Requests are limited to 256 KiB. Calls use the target's declared environment and timeout, inherit cancellation from the parent and stop when the parent completes or times out. Cycles are rejected, at most four nested route calls are allowed, and each root invocation has a shared budget of sixteen route calls.

`auth: "mukai"` is authorized by the controller for these workspace-scoped internal calls. No HTTP listener, host URL or API token is needed, and Mukai authorization headers are removed before delivery to custom handlers for both internal and authenticated HTTP calls. `auth: "handler"` still runs the handler's signature checks against the supplied headers and exact raw bytes. External HTTP authentication remains required as before. To test a route from chat, the bot can create and register a custom tool that calls `context.callRoute`, with a permission mode appropriate to the route's effects; the new tool is then callable in the normal tool loop. This works in local and VM workspaces.

Authentication is explicit: `mukai` requires the local API bearer token; `handler` requires your handler to verify the provider signature before work or queue acceptance; `public` declares an unauthenticated endpoint. `request.rawBody` contains the original bytes, and `request.body` contains parsed JSON when appropriate. The generic HMAC example is not a Stripe verifier: use each provider's documented signing algorithm or SDK.

Bot-facing custom tool results include a Mukai-generated receipt: `{permission:{mode,approvedBy,decision},execution,result? ,error?}`. `approvedBy` is `user` for actual user decisions, `bot` for bot continuation/cancellation, or `runtime` for automatic approval. Decisions are `approved`, `auto_approved`, `denied`, or `cancelled`. Execution is separately `completed`, `failed`, or `not_executed`: approval does not guarantee success, and a failed execution may have partial effects. Module output stays nested under `result`, so a module cannot overwrite the runtime receipt. No approver identity, timestamp, or exactly-once guarantee is inferred. The receipt is retained with the normal saved tool result, including restored approvals. The initial `ask_bot` checkpoint remains `confirmation_required`; the receipt arrives when that call is resolved.

Use Settings → Environment variables to save configuration or preview and import a `.env` block. Read only declared names through `context.env`; never hard-code credentials or write them into chat. Values are encrypted in SQLite using the existing credentials key outside the database. Variables are workspace-scoped and resolved per invocation. Empty/missing required values leave registrations visible as Needs configuration. Values are never returned by management APIs. Custom stdout/stderr is discarded; known secrets are redacted from returned strings, run errors, and diagnostics. This cannot stop trusted code from deliberately encoding or exfiltrating secrets.

Install Node dependencies in the workspace's package setup before registering. Static local and package imports are bundled into an immutable compiled version, with workspace source snapshots retained. Node built-ins remain available. Avoid dynamic imports/requires and runtime-relative resource files: these are not automatically captured by bundling. Import-time validation runs in a worker with a five-second deadline and does not call execute/handle. Imports themselves execute top-level JavaScript, so keep top-level code free of side effects. Failed updates preserve the active version. Saved compiled versions reload at startup and remain independent of later workspace edits.

Handlers run in managed Node workers with a default 15-second deadline, configurable `timeoutMs` from 100 to 30,000 ms, an eight-worker concurrency limit, a 128 MiB V8 old-generation heap limit, and a 256 KiB serialized-result limit. HTTP bodies are limited to 1 MiB. Use `context.signal` for cancellable operations. Mukai terminates stuck/cancelled workers. Workers do not inherit the server's environment. This is execution control, not an OS sandbox: code has the current user's filesystem/network access and can spawn its own unmanaged processes. Terminating a worker does not roll back external effects or terminate processes it spawned. Never open another HTTP listener.

For durable webhooks, verify authenticity, then `await context.enqueue(provider,eventId,payload)` before acknowledging. Define `processJob(payload,context)` in the route module to do background work. Deduplication is scoped to registration + provider + event ID. Payloads are encrypted at rest, versions are pinned, and interrupted jobs resume after restart. Completed jobs discard their payload while retaining deduplication IDs. Failed jobs retry up to five attempts with backoff and appear in the inspector. Delivery is at least once; use provider event IDs to make external writes idempotent. Disabling a registration pauses queued work; deleting it removes its jobs, runs, and deduplication records. Source snapshots are retained for existing calls and recovery.

Receiving a webhook never calls a model automatically. `await context.wakeBot(message)` explicitly commits a wake-up job for the registration's owner bot. Use `await context.wakeBot(message, { botId: 'target-bot-id' })` to select a bot in the same workspace. Bot-owned registrations may wake their owner, or peers/lower-level bots permitted by the owner's current `manage_bot` access. Registrations created through the UI have no owner and require an explicit bot ID. Invalid targets fail without falling back; target access is checked both before queue acceptance and before execution. Awaiting the helper saves the job, without waiting for a model response, so the handler can immediately acknowledge the webhook. Each wake-up starts a new private conversation for the target bot; retries reuse that conversation. Wakes retry while the target bot is busy. For delivery deduplication, enqueue the provider event ID and call wakeBot from processJob. Treat external event content as data, not instructions. Mukai must remain running to receive and process requests.

Set the public base URL in **Settings → Domain** (for example, `https://your-host.example`) to display public route URLs and permit that ingress Host. Without it, the UI displays full local URLs. The backend stays on loopback: use an HTTPS reverse proxy/tunnel forwarding only `/custom/*` to its current port, and do not expose management APIs. The desktop uses fixed port 47831; standalone mode defaults to the same port and can be overridden with `PORT`. The base URL setting does not itself create a tunnel or deploy the app. Provider webhooks require an externally reachable HTTPS address.
